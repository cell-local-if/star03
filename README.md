# Digital Content Provenance Evidence Network

This repository is the backend for a digital content provenance evidence network. Its long-term purpose is to let systems register digital content, identify its source, attach verifiable claims and evidence, connect revisions and derivatives, and independently verify the resulting provenance graph.

The production roadmap must stay within backend engineering. It should grow through independently testable capabilities covering content identities and digests, source actors, claims, evidence bundles, attestations, signatures, version lineage, derivation edges, verification, revocation, trust policy, authorization, audit history, search, import and export, asynchronous processing, idempotency, concurrency, migrations, privacy, observability, recovery, and interoperability.

## Public engineering contract

- Python 3.12 is the runtime. The initial persistence target is SQLite. New dependencies must be declared and locked.
- The stable command-line entry point is `python -m provenance`. HTTP interfaces, when present, use JSON and expose explicit versioned routes.
- Persisted identifiers are stable. Timestamps use timezone-aware UTC. Hashes, signatures, and canonical encodings declare their algorithms and reject malformed input.
- Mutating operations are transactional and idempotent where clients can retry. Validation errors are distinct from missing resources, conflicts, authorization failures, and internal failures.
- Provenance history is append-oriented. Corrections, supersession, expiry, and revocation preserve the earlier evidence and their audit relationship.
- Tests must be deterministic and run without external network access. Security-sensitive behavior requires negative and boundary coverage.
- Secrets, credentials, private keys, and raw copyrighted content do not enter the repository or logs. Content bytes are referenced by digest and metadata unless a later public requirement explicitly defines controlled storage.
- Every change must preserve documented APIs and stored data unless it includes an explicit compatibility and migration path.

The baseline intentionally contains only this public contract. The first production task must create a complete runnable backend capability that does not already exist here; later tasks must build on reviewed, selected commits without repeating earlier work.

## Running the service

```bash
python -m provenance                      # uses sqlite:///./provenance.db
python -m provenance --database-url sqlite:////var/lib/provenance.db --port 8080
PROVENANCE_DATABASE_URL=sqlite:///./x.db python -m provenance
```

The database location is taken from `--database-url`, then the `PROVENANCE_DATABASE_URL` environment variable, then the default. Tables are created automatically on first startup (parent directories included).

## Initial capability: content identity and source actors

Versioned JSON routes under `/v1`:

- `POST /v1/actors` — register a source actor (`id`, `name`, `type`); returns `201`.
- `POST /v1/contents` — register content identity by digest. Requires an existing actor; validates `digest_algorithm=sha256`, exactly 64 hexadecimal characters for `digest_hex`, and non-empty `media_type`/`actor_id`. The first registration returns `201`; a repeat submission for the same algorithm+digest returns `200` with the existing resource and no new id or audit event. Content bytes are never accepted, stored, or logged — only the digest and metadata.
- `GET /v1/contents/{content_id}` — full public fields, or `404 content_not_found`.
- `GET /v1/contents?actor_id=...` — contents in stable creation order, optionally filtered by source actor.

## Immutable content claims

Claims attach a typed, digest-committed statement by an actor to a registered content identity. Claims are immutable and append-only: there is no update or delete path.

- `POST /v1/claims` — create a claim with `content_id`, `actor_id`, non-empty `claim_type`, and a JSON-object `payload`. Both the content and the actor must already exist; the claiming actor need not be the content's registering actor. The server computes a SHA-256 digest over a deterministic canonical JSON serialization of the payload (sorted keys, minimal separators, UTF-8) and stores only the digest — the raw payload is never persisted or echoed. The first creation returns `201` with the stable claim id, associations, digest algorithm and value, and UTC `created_at`; a repeat submission with the same content, actor, claim type, and canonical payload returns `200` with the existing claim and adds no audit event. Any different field combination forms an independent claim.
- `GET /v1/claims/{claim_id}` — full public fields, or `404 claim_not_found`.
- `GET /v1/claims?content_id=...&actor_id=...&claim_type=...&payload_digest_hex=...&limit=...&cursor=...` — read-only reviewer search over existing immutable claims. The success body is `{"items", "count", "next_cursor"}`, each item being the existing claim public view (associations, digest algorithm/value, and UTC `created_at`; the raw payload is never stored and so is never echoed), in the claims' stable creation order. Optional `content_id`, `actor_id`, and `claim_type` are non-empty, case/whitespace-sensitive exact matches that combine as logical AND (absent means unfiltered); `payload_digest_hex` must be exactly 64 lowercase hexadecimal characters (uppercase, padded, or wrong-length spellings are `422`, never normalized). `count` is the filtered total independent of the page. `limit` is a pure decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token that binds to every effective filter and the limit, so pages resume without duplication or omission and the final page carries `next_cursor: null`. Blank/illegal/repeated/undeclared parameters and an empty, whitespace-only, malformed, tampered, foreign-family, or query-mismatching `cursor` are `422 validation_error` (nothing is silently defaulted); no match is an empty collection with `count` 0, not a 404. The query and its failures write no claim, resource, or audit row.
- `GET /v1/contents/{content_id}/claims` — that content's claims only, in stable creation order as `{"items", "count"}`; an unknown content id is `404 content_not_found`.

The first claim creation and its `claim.created` audit event commit in a single transaction. Non-object payloads, blank claim types, and malformed JSON are `422 validation_error`; unknown contents and actors remain `404 content_not_found` / `unknown_actor`.

## Immutable claim supersessions

A supersession is an immutable statement that one existing claim supersedes another as a correction of the *same* content's provenance. Neither endpoint claim is mutated or deleted: the original claim and its `claim.created` audit relationship are preserved. Supersessions are append-only: there is no update or delete path.

- `POST /v1/claim-supersessions` — body contains exactly `superseded_claim_id`, `replacement_claim_id`, and a non-empty `reason` (surrounding whitespace is trimmed); any undeclared field is rejected. Both endpoints must be existing claims about the same content, the two ids must differ, and the new edge must not close a supersession cycle. The first creation returns `201` with exactly `{id, superseded_claim_id, replacement_claim_id, reason, created_at}` — a stable `csp_` id and a UTC `created_at` — and commits together with the `claim.superseded` audit event in a single transaction. A retry of the same three fields returns `200` with the original record and writes no new row or audit event; a different reason forms an independently retained record.
- `GET /v1/claim-supersessions/{supersession_id}` — full public fields, or `404 claim_supersession_not_found` whose details carry the requested `supersession_id`.
- `GET /v1/claims/{claim_id}/supersessions` — the records where the claim is either endpoint, in stable creation order as `{"items", "count"}`; an unknown claim id is the existing `404 claim_not_found` (a missing claim is never an empty collection).
- `GET /v1/claims/{claim_id}/supersession-lineage?direction=newer|older&max_depth=...&min_depth=...&limit=...&cursor=...` — read-only reviewer multi-hop traversal of the supersession graph. `direction` is required and must be exactly `newer` (from the superseded claim onward to each `replacement_claim_id`) or `older` (the reverse, to each `superseded_claim_id`); `max_depth` is an optional pure decimal integer from 1 to 32 defaulting to 8. Optional depth floor and paging: `min_depth` is a pure decimal integer from 1 to 32 defaulting to 1 and must not exceed the effective `max_depth`; `limit` is a pure decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token (its own `sl1` family) returned by a previous page. `min_depth` only removes returned items — it never prunes traversal reachability, changes shortest-depth dedup, or changes depth/discovery ordering. Missing, blank/whitespace, illegal, or repeated `direction`; an empty, non-integer, out-of-range, or repeated `max_depth`, `min_depth`, or `limit`; an undeclared parameter; a `min_depth` greater than the effective `max_depth`; and an empty, whitespace-only, malformed, tampered, cross-endpoint/foreign-family, or origin/direction/depth/limit-mismatching `cursor` are all `422 validation_error` — nothing is defaulted or silently normalized, and every parameter and the cursor are validated before the origin lookup. The origin claim is never included; only claims reachable within the depth limit are returned, each deduplicated at its shortest depth, ordered by depth ascending and within a level by the discovering supersession record's stable creation order, as `{"items", "count", "next_cursor"}` where each item is the existing claim public view plus an integer `depth` (the raw payload is never echoed). `count` is the total number of items after the `min_depth` filter, independent of the page returned; `next_cursor` is an opaque token for the next page or `null` on the final (and only, for an empty result) page. The first page carries no `cursor`; a continuation carries the previous response's `next_cursor` together with the same origin, direction, and every effective condition, and pages then resume without duplication or omission — replaying a cursor returns the same page, and a cursor at or past the tail returns empty `items` with the original `count` and `next_cursor: null`. Cursors bind to the origin, direction, the effective `max_depth`/`min_depth`, and the effective `limit`. No reachable claims yields an empty set. An unknown origin claim is the existing `404 claim_not_found`, decided only after query validation. The query reads only claims and supersessions (no resource, supersession, or audit writes), deduplicates visited nodes, and terminates even if anomalous history contains a cycle.

An unknown claim on either side is `404 claim_not_found` (matched by the declared endpoint field). Blank or whitespace-only fields, missing fields, undeclared fields, wrong-typed values, malformed JSON, endpoints on different contents, self-supersession, and an edge that would close a cycle are all `422 validation_error` and write neither a record nor an audit event. Reads and failed requests write no resource and no audit event; the public views never echo claim payloads, signatures, content, or evidence bytes.

## Verifiable evidence bundles

Evidence bundles attach externally verifiable evidence to an existing claim by digest alone. The raw evidence bytes are never accepted, persisted, or logged — only the digest algorithm/value, media type, and a metadata object are stored. Bundles are immutable and append-only: there is no update or delete path.

- `POST /v1/evidence-bundles` — create a bundle with an existing `claim_id`, a non-empty `evidence_type`, `digest_algorithm`, `digest_hex`, a non-empty `media_type`, and a JSON-object `metadata`. Only `digest_algorithm=sha256` with exactly 64 hexadecimal characters is accepted (hex is case-normalized, as for contents). The first creation returns `201` with the stable bundle id, claim association, evidence type, digest algorithm and value, media type, metadata, and UTC `created_at`; a repeat submission with the same claim, evidence type, and digest returns `200` with the existing bundle — its first-submission metadata and media type are retained — and adds no audit event. Any different field combination forms an independent bundle.
- `GET /v1/evidence-bundles/{evidence_bundle_id}` — full public fields, or `404 evidence_bundle_not_found`.
- `GET /v1/evidence-bundles?claim_id=...&evidence_type=...&media_type=...&digest_hex=...&limit=...&cursor=...` — read-only reviewer search over all existing evidence bundles. The success body is `{"items", "count", "next_cursor"}`, each item being the existing evidence-bundle public view (associations, digest algorithm/value, media type, metadata, and UTC `created_at`; evidence bytes are never stored and so are never echoed), in the bundles' stable creation order. Optional `claim_id`, `evidence_type`, and `media_type` are non-empty, case/whitespace-sensitive exact matches that combine as logical AND (absent means unfiltered); `digest_hex` must be exactly 64 lowercase hexadecimal characters (uppercase, padded, or wrong-length spellings are `422`, never normalized). `count` is the filtered total independent of the page. `limit` is a pure decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token that binds to every effective filter and the limit, so pages resume without duplication or omission and the final page carries `next_cursor: null`. Blank/illegal/repeated/undeclared parameters and an empty, whitespace-only, malformed, tampered, foreign-family, or query-mismatching `cursor` are `422 validation_error` (nothing is silently defaulted); no match is an empty collection with `count` 0, not a 404, and filter values are never resolved for existence. The query and its failures write no bundle, resource, or audit row.
- `GET /v1/claims/{claim_id}/evidence-bundles` — that claim's bundles only, in stable creation order as `{"items", "count"}`; an unknown claim id is `404 claim_not_found` (a missing claim is never an empty collection).
- `GET /v1/contents/{content_id}/evidence-bundles?evidence_type=...&media_type=...&limit=...&cursor=...` — read-only listing for reviewers of the evidence attached to one content. It returns only bundles linked through claims that directly assert this exact content; it does not traverse lineage to ancestor/descendant contents and never returns raw bytes. Optional `evidence_type` and `media_type` are non-empty, case/whitespace-sensitive exact matches that combine as logical AND; absent means unfiltered. Results follow the bundles' stable creation order (across all of the content's claims) as `{"items", "count", "next_cursor"}` where each item is the existing evidence-bundle public view and `count` is the filtered total, independent of the page. `limit` is an integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token that binds to the origin and every effective filter/limit, so pages resume without duplication or omission and the final page carries `next_cursor: null`. Blank/illegal/repeated/mismatching parameters and an empty, malformed, tampered, foreign-family, or query-mismatching `cursor` are `422 validation_error` (nothing is silently defaulted); an unknown content id is `404 content_not_found`. The query writes no resource or audit rows.
- `GET /v1/contents/{content_id}/export` — read-only provenance-evidence snapshot of one content, for handover to third-party verifiers. The success body is exactly `{"content", "claims"}`: `content` is the full public content view, and `claims` lists the claims that directly assert this exact content in stable creation order, each as the full public claim view plus an `evidence_bundles` array of that claim's bundles in stable creation order (each the full public bundle view). No lineage traversal is performed and no other content, claim, or bundle is ever included; raw content, claim payloads, and evidence bytes never appear. A content without claims yields `"claims": []`; a claim without bundles yields an empty `evidence_bundles` array. The route accepts no query parameters — any parameter is `422 validation_error` — and an unknown content id is `404 content_not_found`. Reads, empty results, and failures write no resource or audit rows.
- `GET /v1/evidence-bundles/{evidence_bundle_id}/exchange` — read-only evidence-bundle interoperability snapshot for external verifiers. The success body is exactly `{"content", "claim", "evidence_bundle", "attestations"}`: `content` is the full public view of the content the bundle's directly associated claim asserts, `claim` is the full public view of the single claim the bundle is directly attached to, `evidence_bundle` is the bundle's existing full public view, and `attestations` lists only the existing attestations whose target type is `evidence_bundle` and whose target id equals this bundle, in stable creation order, each with exactly the existing attestation detail fields (a revoked attestation is retained so the snapshot stays historically auditable). The content graph is never expanded through lineage and no other content, claim, bundle, or attestation is ever included; the raw signature, claim payload, content bytes, and evidence bytes are neither stored nor echoed. A bundle with no attestations yields `"attestations": []`. The route accepts no query parameters — any parameter or repeated parameter is `422 validation_error` — and an unknown evidence bundle id is the existing `404 evidence_bundle_not_found`. Success, empty attestation lists, and failures create no resource, modify no record, and add no audit event.
- `GET /v1/evidence-bundles/{evidence_bundle_id}/exchange/manifest` — read-only integrity manifest for the exchange snapshot above. The success body is exactly `{"manifest_version", "evidence_bundle_id", "digest_algorithm", "manifest_digest_hex"}`: `manifest_version` is fixed at `provenance-exchange-manifest-v1` and `digest_algorithm` is fixed at `sha256`. `manifest_digest_hex` is the SHA-256 hex digest of the canonical JSON object built from exactly the snapshot's `content`, `claim`, `evidence_bundle`, and `attestations` members: the root member names and array element order are kept exactly as in the snapshot, nested object members are ordered by Unicode code point, and serialization uses compact separators, unescaped non-ASCII characters, and UTF-8 encoding. No other resource, internal sequence number, raw signature, claim payload, content bytes, or evidence bytes participate in the digest; a revoked attestation is not removed from the snapshot and therefore still contributes. The same persisted state always yields the same manifest on repeated reads (including across an app restart). The route accepts no query parameters — any parameter or repeated parameter is `422 validation_error`, validated before the bundle lookup — and an unknown evidence bundle id is the existing `404 evidence_bundle_not_found`. Reads and failures create no resource, modify no record, and add no audit event; the existing snapshot, identifiers, UTC fields, and error JSON are unchanged.
- `GET /v1/evidence-bundles/{evidence_bundle_id}/exchange/package` — read-only one-call export of the exchange snapshot together with its integrity manifest. The success body is exactly `{"snapshot", "manifest"}`: `snapshot` is exactly the four-member body of the existing `GET .../exchange` route (`content`, `claim`, `evidence_bundle`, `attestations`, each the existing public view), and `manifest` is exactly the four-field body of the existing `GET .../exchange/manifest` route. The manifest digest is computed over exactly the `snapshot` member returned in the same response under the existing canonical rules (root members and array element order kept, nested object keys sorted by Unicode code point, compact separators, unescaped non-ASCII, UTF-8), and both halves derive from a single snapshot read, so they are always mutually consistent. No lineage is traversed and no other resource, internal sequence number, raw signature, claim payload, content bytes, or evidence bytes are included; a bundle with no attestations yields `"attestations": []` with the digest computed over that empty array. The route accepts no query parameters — any parameter or repeated parameter is `422 validation_error`, validated before the bundle lookup — and an unknown evidence bundle id is the existing `404 evidence_bundle_not_found`. Success, empty attestation lists, and failures create no resource, modify no record, and add no audit event; repeated reads and reads across an app restart return the same package, and the existing exchange route, manifest route, identifiers, UTC fields, and error JSON are unchanged.
- `POST /v1/exchange-manifest-verifications` — stateless offline verification of a received exchange snapshot against its integrity manifest, for third-party verifiers. The request body is exactly `{"manifest_version", "evidence_bundle_id", "digest_algorithm", "manifest_digest_hex", "snapshot"}`: `manifest_version` must be `provenance-exchange-manifest-v1`, `digest_algorithm` must be `sha256`, and `manifest_digest_hex` must be exactly 64 lowercase hexadecimal characters. `snapshot` is exactly `{"content", "claim", "evidence_bundle", "attestations"}` whose nested objects carry exactly the existing public-view fields; `evidence_bundle.id` must equal the manifest's `evidence_bundle_id`, `claim.id` must equal `evidence_bundle.claim_id`, `content.id` must equal `claim.content_id`, and every attestation must have `target_type: "evidence_bundle"` with `target_id` equal to the manifest's bundle id. The snapshot is canonicalized under the existing manifest rules (root members and array elements keep their received order, nested object members sort by Unicode code point, compact separators, unescaped non-ASCII, UTF-8) and hashed with SHA-256. Any structural, field, association, or raw-material violation is `422 validation_error`; a structurally valid request whose computed digest differs is `200 {"valid": false, "computed_digest_hex": ...}`, and a match is exactly `{"valid": true}`. The route is purely a function of the request body: it never queries, creates, or modifies any local resource or audit record, so unknown bundle ids verify exactly like known ones.
- `POST /v1/evidence-bundle-exchange-imports` — controlled registration of an exchange package already received and verified offline, for an external forensics system. The request body is exactly `{"manifest", "snapshot"}`: `manifest` is the existing four-field exchange manifest (`manifest_version`, `evidence_bundle_id`, `digest_algorithm`, `manifest_digest_hex`) and `snapshot` is the existing four-member exchange snapshot (`content`, `claim`, `evidence_bundle`, `attestations`), both validated exactly as on the stateless verification route — fixed `provenance-exchange-manifest-v1` version and `sha256` algorithm, a 64-lowercase-hex manifest digest, existing public-view fields only, and the same internal associations (bundle id matches the manifest, the claim matches the bundle, the content matches the claim, every attestation targets this exact bundle). The snapshot is canonicalized under the existing manifest rules over the raw received JSON (root member and array order kept, nested object keys sorted by Unicode code point, compact separators, unescaped non-ASCII, UTF-8) and hashed with SHA-256; the computed digest must equal the manifest's claimed digest. Verification is decided by the request body alone and never resolves any identifier against local resources, so whether the referenced content, claim, bundle, or attestations exist locally cannot change the verdict, and no such resource is created. No field can carry a raw signature, claim payload, content bytes, or evidence bytes: undeclared fields on any member are rejected. Missing or extra top-level fields, malformed JSON, and every structural, field, association, raw-material, or digest-mismatch failure are `422 validation_error` and write nothing. On success the receiving identity is exactly `(manifest_version, evidence_bundle_id, manifest_digest_hex)`; the first submission returns `201` with a stable deterministic `eir_` receipt id, the three identity fields, and a UTC `received_at`, and writes the receipt row together with the `evidence_bundle.exchange_imported` audit event in a single transaction. A retry for the same identity returns `200` with the original receipt (including its original `received_at`) and writes no second row or audit event — even when the retried snapshot itself no longer matches, in which case the retry is `422` and the original record is untouched. The full snapshot is never copied or persisted: the receipt holds only the identity fields.
- `GET /v1/evidence-bundle-exchange-imports/{import_id}` — read the public receipt for one registered exchange import: exactly `{"id", "manifest_version", "evidence_bundle_id", "manifest_digest_hex", "received_at"}`, with `received_at` a UTC timestamp. The snapshot and every raw material are never returned. An unknown id is an explicit `404 evidence_bundle_exchange_import_not_found` carrying the requested `import_id`; the read is strictly read-only and writes no resource or audit event.
- `GET /v1/evidence-bundle-exchange-imports?manifest_version=...&evidence_bundle_id=...&manifest_digest_hex=...&limit=...&cursor=...` — read-only search over existing exchange-import receipts. The success body is exactly `{"items", "count", "next_cursor"}`; each item is the existing single-receipt public view (`id`, `manifest_version`, `evidence_bundle_id`, `manifest_digest_hex`, UTC `received_at`; the snapshot is never returned) in stable creation order (`created_at` with the monotonic `seq` tiebreaker). Optional `manifest_version`, `evidence_bundle_id`, and `manifest_digest_hex` are non-empty, case- and whitespace-sensitive exact matches that combine as logical AND; absent means unfiltered. `count` is the filtered total, independent of the page. `limit` is a decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token that binds to every effective filter and the limit, so pages resume without duplication or omission and the final page carries `next_cursor: null` (a cursor at or past the end returns an empty page with the total `count`). Blank/illegal/repeated/undeclared parameters and an empty, malformed, tampered, foreign-family, or query-mismatching `cursor` are `422 validation_error` — nothing is silently normalized or defaulted — and no match is an empty collection (`{"items": [], "count": 0, "next_cursor": null}`). The search is strictly read-only: it writes no resource and no audit event.
- `GET /v1/evidence-bundle-exchange-imports/{import_id}/reconciliation` — read-only reconciliation of one registered exchange-import receipt against current local state. The receipt is read by `import_id`; an unknown id is the existing `404 evidence_bundle_exchange_import_not_found`. The success body is exactly `{"import_id", "local_available", "local_manifest_digest_hex", "matches"}`. The receipt's `evidence_bundle_id` is the only local lookup key — the bundle is resolved by that id alone, never by a reverse digest or receipt search — and when no local bundle has that id the body is `(receipt id, false, null, false)` with a `200`. When a local bundle exists, `local_available` is `true` and `local_manifest_digest_hex` is the bundle's current digest computed under exactly the `GET /v1/evidence-bundles/{evidence_bundle_id}/exchange/manifest` rules; `matches` is `true` only when that digest equals the receipt's `manifest_digest_hex` character for character, otherwise `false`. The route accepts no query parameters — any parameter or repeated parameter is `422 validation_error`, validated before the receipt lookup. The snapshot, raw signatures, payloads, and bytes are never echoed; the read is strictly read-only and writes no resource, receipt, or audit event, and the existing error JSON, identifiers, and UTC fields are unchanged.
- `GET /v1/evidence-bundle-exchange-import-reconciliations?local_available=...&matches=...&limit=...&cursor=...` — read-only, paginated reconciliation of every existing exchange-import receipt against current local state. Only `local_available`, `matches`, `limit`, and `cursor` are accepted: any unknown, repeated, blank, or illegal parameter is `422 validation_error`. The success body is strictly `{"items", "count", "next_cursor"}`; receipts are returned in the same stable creation order (`created_at` with the monotonic `seq` tiebreaker), filtered items keep that order, and `count` is the total number of receipts matching the active filters, independent of the page. Each item is the existing single-receipt public view (`id`, `manifest_version`, `evidence_bundle_id`, `manifest_digest_hex`, UTC `received_at`) plus `local_available`, `local_manifest_digest_hex`, and `matches`; each item is reconciled using only its own `evidence_bundle_id` under exactly the single-receipt reconciliation rules — no local bundle gives `false`/`null`/`false`; when a local bundle exists its current exchange manifest digest is reported and `matches` is `true` only on character-for-character equality with the receipt digest. The optional `local_available` and `matches` filters are each provided at most once and accept only the lowercase literals `true` or `false` (blank, capitalized, numeric, or other spellings are `422`); an absent filter imposes no restriction and the two combine as logical AND against the fields computed at that read (there is no reverse lookup by digest or any other resource). Note that `matches=false` keeps both unavailable and available-but-diverged receipts, while `local_available=false&matches=true` can never match and is therefore a 200 empty collection. `limit` is a decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token (its own `ir1` family) binding to both effective filters (`null` when unfiltered) and the effective limit, so pages resume without duplication or omission and the final page carries `next_cursor: null` (a cursor at or past the end of the filtered set returns an empty page with the filtered `count`; an empty, malformed, tampered, foreign-family, or filter/limit-mismatching cursor is `422 validation_error`). Parameters and the cursor are all validated before any receipt or local bundle is read; no matching receipts is an empty collection (`{"items": [], "count": 0, "next_cursor": null}`). The snapshot, raw signatures, payloads, and bytes are never echoed; the route is strictly read-only and writes no resource, receipt, or audit event on success or failure, and it is compatible with the existing single-receipt reconciliation, the unfiltered collection behavior, and the error JSON.

The first bundle creation and its `evidence_bundle.created` audit event commit in a single transaction. Blank text fields, non-object metadata, unsupported algorithms or malformed digests, malformed JSON, and **any undeclared request field** are `422 validation_error`; an unknown claim on creation or listing remains `404 claim_not_found`. In particular, fields that could carry raw evidence (for example `data` or `evidence`) are not silently ignored: they are rejected with `422` and write neither a resource nor an audit event.

## Asynchronous content export jobs

An export job is a server-tracked, runnable resource that produces the read-only content provenance-evidence snapshot (see `GET /v1/contents/{content_id}/export`) asynchronously. Jobs are append-oriented: each moves monotonically through `pending` → `running` → `succeeded`/`failed`, and a settled or in-flight job can never be claimed or run again. The `request_id` is a client-supplied idempotency key.

- `POST /v1/content-export-jobs` — body contains exactly an existing non-empty `content_id` and a non-empty client-supplied `request_id` (surrounding whitespace is trimmed); any undeclared field is rejected. The first submission returns `201` with exactly `{id, content_id, request_id, status, created_at, started_at, finished_at, result, error}` — a stable deterministic `cxj_` id, `status: "pending"`, a timezone-aware UTC `created_at`, and `started_at`, `finished_at`, `result`, and `error` all `null` — and writes the job row together with the `content_export_job.created` audit event in a single transaction. A retried submission for the same `(request_id, content_id)` returns `200` with the original job in whatever its current lifecycle state is and writes no second row or audit event. Reusing the same `request_id` for a *different* `content_id` is `409 content_export_request_conflict` and writes nothing. Missing/blank/whitespace fields, wrong-typed or null values, malformed JSON, and undeclared fields are `422 validation_error`; an unknown content id is `404 content_not_found`.
- `GET /v1/content-export-jobs/{job_id}` — returns one job's public view with exactly the nine fields above, or `404 content_export_job_not_found` (whose details carry the requested `job_id`). The read is strictly read-only: it writes no job and no audit event.
- `GET /v1/content-export-jobs?content_id=...&request_id=...&status=...&from=...&to=...&limit=...&cursor=...` — read-only cross-job search over existing content export jobs. The request body must be empty: carrying any body is `422 validation_error`, rejected before any parameter or job is read. The success body is exactly `{"items", "count", "next_cursor"}`; each item is the existing single-job public view (the nine fields above, including a settled job's `result` snapshot, which itself carries only the existing public views — never raw content, claim payloads, or evidence bytes), and items follow the jobs' stable creation order (`created_at` with the monotonic `seq` tiebreaker). Optional `content_id`, `request_id`, and `status` combine as logical AND; `content_id`/`request_id` are non-empty, case/whitespace-sensitive exact matches (absent means unfiltered) and are never resolved for existence — an unknown content or request id is an empty collection, not an error. `status` accepts only the four existing lifecycle literals `pending`, `running`, `succeeded`, `failed` (case-sensitive; blank, capitalized, or any other spelling is `422`, never normalized), and absent means no status filtering. `from` and `to` are strict RFC 3339 UTC instants (`Z` or `+00:00`) applied as inclusive `created_at` bounds, and `from` must not be later than `to`. `count` is the filtered total covering every page, independent of the page returned. `limit` is a pure decimal integer from 1 to 100 defaulting to 50 (no sign, decimal point, or whitespace); `cursor` is an opaque HMAC-signed server token in its own `cx1` family, bound to every effective filter (including `null` filters) and the effective limit, so pages resume without duplication or omission, replay the same page when reused, and the final page carries `next_cursor: null` (a cursor at or past the tail returns an empty page with the same filtered `count`). Empty/blank/illegal/repeated/undeclared parameters, a `from` later than `to`, and an empty, whitespace-only, malformed, tampered, wrong-signature, cross-endpoint/foreign-family, or filter/limit-mismatching `cursor` are all `422 validation_error` — parameters and the cursor are validated before any job is read and nothing is silently defaulted. No match returns `{"items": [], "count": 0, "next_cursor": null}`. The success body is compact UTF-8 JSON (compact separators, unescaped non-ASCII) terminated by exactly one newline; timestamps stay UTC, booleans and `null` are rendered as such, and all numbers are integral (no `-0.0` or non-finite values). Each read mints a fresh opaque cursor; the search is strictly read-only — it creates no job, changes no state, writes no audit event, and never returns attachments or raw content, payload, or evidence bytes. Job status may change between queries while ids and creation order stay stable, so the same status filter recomputes consistently across a restart.
- `POST /v1/content-export-jobs/{job_id}/run` — atomically claims a `pending` job and runs it to completion in one transaction. The `pending → running` transition is a single conditional `UPDATE ... WHERE status = 'pending'` that stamps a timezone-aware UTC `started_at`, so of concurrent or repeated calls exactly one claims the job and any other — a concurrent loser, or a repeat call once the job has settled — returns `409 conflict` without changing state or writing an audit event. The winning run builds the existing read-only content export and settles exactly once: on success it returns `200` with `status: "succeeded"`, a timezone-aware UTC `finished_at`, `error: null`, and `result` equal to the body of `GET /v1/contents/{content_id}/export` (exactly `{"content", "claims"}`, claims for this content only in stable order each with its evidence bundles); if the export raises, it returns `200` with `status: "failed"`, a UTC `finished_at`, `result: null`, and `error: "content_export_failed"`. Either settlement records the `content_export_job.run` audit event in the same transaction, so the job is never left stuck in `running`. An unknown job id is `404 content_export_job_not_found`. The run never traverses lineage, never mutates any content/claim/bundle, and its `result` carries only the existing public views — never raw content, claim payloads, or evidence bytes.
- `POST /v1/content-export-jobs/run-next` — server-side queue claim: selects the single oldest `pending` job in the same stable creation order (`created_at` with the monotonic `seq` tiebreaker, which stays stable across an app restart) and immediately performs exactly one atomic run under the single-job run semantics above. The request body must be empty and the route accepts no query parameters: any non-empty body (including whitespace, malformed JSON, a JSON object, or any extra field) and any query parameter (including a blank or repeated parameter) is `422 validation_error`, rejected before any job is read. When at least one job is pending it returns `200` with the claimed job's complete nine-field public view: success settles `succeeded` with UTC `started_at`/`finished_at` and `result` identical to the existing content export snapshot; an export that raises settles `failed` with UTC `finished_at`, `result: null`, and `error: "content_export_failed"` (still `200`); either settlement writes the `content_export_job.run` audit event in the same transaction. Only the oldest pending job is claimed — every other pending job, including younger jobs, remains queued unchanged — and a second call then claims the next oldest. When no job is pending it returns `404 content_export_job_not_found` with zero writes (no job, resource, or audit row). The claim uses the same conditional `UPDATE ... WHERE status = 'pending'` as the single-job run, so of concurrent calls at most one wins any given job: a concurrent loser that picked the same oldest job before it was claimed gets `409 conflict` without modifying any job, creating any resource, or writing an audit event, and it never falls through to a younger queued job. The route never traverses lineage, changes the export snapshot's fields/order/UTC/error JSON, or alters job creation, detail, single-job run, idempotent retry, or `request_id` conflict semantics.
- `GET /v1/content-export-jobs/summary` — read-only queue summary over all existing content export jobs. The request body must be empty and the route accepts no query parameters: any non-empty body (including whitespace, malformed JSON, a JSON object, or any extra field) and any query parameter (unknown, blank, or repeated) is `422 validation_error`, and both validations complete before any job is read, so an invalid request never produces a partial summary. The success body is exactly `{"pending", "running", "succeeded", "failed", "oldest_pending_id", "oldest_pending_wait_seconds"}`: the four counts cover every existing job keyed by its current lifecycle state (settled jobs remain in their `succeeded`/`failed` counts), computed from the current persisted state at read time; `oldest_pending_id` is the stable id of the single oldest `pending` job in the stable creation order (`created_at` with the monotonic `seq` tiebreaker), and `oldest_pending_wait_seconds` is the current UTC instant minus that job's `created_at`, floored to whole integer seconds. On an empty queue every count is zero and both oldest-pending members are `null`. The success body is compact UTF-8 JSON (compact separators, unescaped non-ASCII) terminated by exactly one newline; all numbers are integral (no `-0.0` or non-finite values). The summary is strictly read-only — success, empty results, and failures create no job, modify no resource, and write no audit event — and it freezes nothing: job status may change between reads, while the same persisted state read across an app restart returns the same counts and the same stable oldest id, with the wait time recomputed at each read's own instant. Job creation, detail, search, single-job run, queue claim, idempotent retry, `request_id` conflict, and export snapshot semantics are unchanged.

- `POST /v1/content-export-verifications` — stateless offline integrity verification of a received content export snapshot, for third-party verifiers. The request body is exactly `{"snapshot", "digest_algorithm", "digest_hex"}`: `digest_algorithm` must be `sha256` and `digest_hex` must be exactly 64 lowercase hexadecimal characters. `snapshot` is the existing public content export snapshot — exactly `{"content", "claims"}` whose nested objects carry exactly the existing public-view fields: `content` is the full public content view, and `claims` lists the claims that directly assert this exact content, each the full public claim view plus an `evidence_bundles` array of that claim's bundles (each the full public bundle view); every claim's `content_id` must equal `snapshot.content.id`, and every bundle's `claim_id` must equal its enclosing claim's `id`. An empty `claims` list is a legal snapshot and the recomputed digest still covers that empty array. The snapshot is canonicalized under fixed rules (root member order and array element order kept, nested object keys sorted by Unicode code point, compact separators, unescaped non-ASCII, UTF-8) and hashed with SHA-256. A match returns `200` with exactly `{"valid": true}`; a structurally valid request whose recomputed digest differs returns `200` with exactly `{"valid": false, "computed_digest_hex": ...}`. Missing or extra top-level or nested fields, wrong member types, malformed JSON, a wrong algorithm, a malformed digest (uppercase, wrong length, non-hex, null, wrong type), an internally inconsistent snapshot (a claim on another content, a bundle attached to another claim), and any field carrying raw content bytes, a claim `payload`, evidence bytes, or a raw signature are all `422 validation_error` and never echo the submitted material. The route accepts no query parameters — any parameter is `422 validation_error`. It is purely a function of the request body: it never queries, creates, or modifies any resource, snapshot, audit record, or log, never saves raw material, and never traverses lineage, so unknown resources and repeated requests verify identically whether or not anything exists locally. The success body is compact UTF-8 JSON (compact separators, unescaped non-ASCII) terminated by exactly one newline; numbers stay integral (no `-0.0` or non-finite values). The existing content export fields, field order, UTC time format, error JSON structure, and persistence compatibility are unchanged.

## Verifiable attestations

Attestations cryptographically bind an existing signing actor to an existing claim or evidence bundle. They only associate targets that already exist; they never create claims, bundles, or actors. The service verifies Ed25519 signatures but never holds a private key, and only verified attestations are ever written.

- `POST /v1/attestations` — body contains `target_type` (`"claim"` or `"evidence_bundle"`), the existing `target_id`, an existing `signer_actor_id`, a Base64 Ed25519 `public_key` that decodes to exactly **32 bytes**, and a Base64 `signature` that decodes to exactly **64 bytes**. The signature is verified against the exact UTF-8 canonical JSON array (compact separators, non-ASCII emitted unescaped):

  ```
  ["provenance-attestation-v1",target_type,target_id,signer_actor_id]
  ```

  A signature over any other serialization (reordered elements, whitespace, ASCII `\u` escapes, a different prefix/actor) fails verification. The first creation returns `201` with the stable `att_` id, `target_type`/`target_id`, `signer_actor_id`, the Base64 public key, the `sha256` hex digest of the signature, `verified: true`, and a UTC `created_at`. The raw signature is never persisted or echoed — only its SHA-256 digest is stored. A repeat submission with the same target, signing actor, public key, and signature digest returns `200` with the existing attestation and writes no row or audit event.
- `GET /v1/attestations/{attestation_id}` — full public fields, or `404 attestation_not_found`.
- `GET /v1/attestations?target_type=...&target_id=...` — all attestations in stable creation order as `{"items", "count"}`, optionally filtered by `target_type` (`claim` / `evidence_bundle`; any other value is `422 validation_error`) and/or `target_id`. Filtering is an empty collection (`{"items": [], "count": 0}`), never a 404.

The first attestation write and its `attestation.created` audit event commit in a single transaction. An unknown target is `404 claim_not_found` / `evidence_bundle_not_found` (matched by the declared `target_type`), and an unknown signing actor is `404 unknown_actor` even when the signature itself is valid. Bad Base64, wrong decoded lengths (32/64 bytes), blank identifiers, unknown `target_type`, undeclared fields, and malformed JSON are `422 validation_error`; a well-formed request whose signature fails verification is `422 attestation_verification_failed`, with no resource or audit write. Signature verification uses an RFC 8032 Ed25519 implementation in the Python standard library (no external crypto dependency).

## Trust evaluation for reviewers

Reviewers can ask the service to evaluate how many independent signing subjects have verified a given claim or evidence bundle. The evaluation is purely read-only: it computes its answer from the attestations already stored and creates neither a resource nor an audit event.

- `GET /v1/trust-evaluations?target_type=claim|evidence_bundle&target_id=...&min_signers=...` — `target_type` is required and must be exactly `claim` or `evidence_bundle`; `target_id` is required and non-blank. `min_signers` is optional and must be a plain decimal integer from 1 to 100, defaulting to 1 (no sign, decimal point, or leading/trailing whitespace). Returns exactly `{"target_type", "target_id", "min_signers", "qualified_signer_count", "decision"}`. Only attestations of the exact target with `verified=true` and **no recorded revocation** are counted (every stored attestation is a verified one, but a revoked attestation is retained for history yet no longer qualifies), and the count is the number of **distinct** `signer_actor_id` values: several attestations by the same actor — for example under different keys — qualify once. If a signer's only attestation of the target is revoked, that actor drops out of the count; a target whose attestations are all revoked evaluates like one with no attestations. `decision` is `trusted` when `qualified_signer_count >= min_signers` and `untrusted` otherwise (an existing target with no qualifying attestations evaluates to zero signers and `untrusted`, not to a 404). The result is computed live on every request. Parameters are fully validated before any existence lookup: missing/blank/unknown/repeated `target_type` or `target_id`, a blank identifier, an undeclared parameter, and a non-integer, out-of-range, signed, or whitespace-bearing `min_signers` are all `422 validation_error` — nothing is silently defaulted or normalized. Once the parameters are valid, a missing target is `404 claim_not_found` or `404 evidence_bundle_not_found` according to the declared `target_type` (declaring an existing bundle's id as a claim, or vice versa, is likewise a 404).

## Immutable attestation revocations

A revocation is an immutable, append-only record that an existing attestation is no longer relied upon. It neither updates nor deletes the attestation: the original proof and its `attestation.created` audit relationship are preserved. There is deliberately no update or delete path for a revocation.

- `POST /v1/attestation-revocations` — body contains the existing `attestation_id`, an existing `revoker_actor_id` (which need not be the attestation's signer), and a non-empty `reason` (surrounding whitespace is trimmed). The first creation returns `201` with the stable `rev_` id, the `attestation_id`/`revoker_actor_id` associations, the reason, and a UTC `created_at`. A repeat submission of the same attestation, revoking actor, and reason returns `200` with the existing record and adds no row or audit event; any different combination (a different revoker or a different reason) forms an independent record that is separately retained. Revocations never accept, store, or echo the original signature.
- `GET /v1/attestation-revocations/{revocation_id}` — full public fields, or `404 attestation_revocation_not_found`.
- `GET /v1/attestations/{attestation_id}/revocations` — that attestation's revocation records only, in stable creation order as `{"items", "count"}`; an unknown attestation id is `404 attestation_not_found` (a missing attestation is never an empty collection).

The first revocation write and its `attestation.revoked` audit event commit in a single transaction. An unknown attestation is `404 attestation_not_found` and an unknown revoking actor is `404 unknown_actor`. Blank or whitespace-only `attestation_id`, `revoker_actor_id`, or `reason`, malformed JSON, and any undeclared request field are `422 validation_error` and write neither a record nor an audit event. Because records are append-only, any attempt to update or delete a revocation is met with `405 method_not_allowed`; no such mutation path is provided.

## Read-only proof access grants

A read-only access grant authorizes another actor to read one existing attestation through a protected endpoint. Grants are immutable and append-only: there is no update or delete path, and a grant never mutates the attestation it references.

Both protected routes authenticate every request with three headers:

- `X-PA` — the calling actor id;
- `X-PT` — the request timestamp as an RFC 3339 UTC instant (`Z` or an explicit `+00:00`; no naive or non-UTC value), no more than **300 seconds** from the server's current time;
- `X-PS` — a standard-Base64 Ed25519 signature (64 raw bytes) over the exact UTF-8 compact JSON array (compact separators, non-ASCII emitted unescaped):

  ```
  ["provenance-access-v1",method,path,timestamp,body_sha256]
  ```

  `method` is the uppercase HTTP method, `path` is the request path without any query string, `timestamp` is the exact `X-PT` header value, and `body_sha256` is the lowercase-hex SHA-256 of the actual request body bytes — the digest of zero bytes for an empty (GET) body. The signature is accepted if it verifies under **any** public key of a non-revoked attestation created by the calling actor; a revoked attestation's key never authenticates.

- `POST /v1/attestation-access-grants` — JSON body contains exactly `attestation_id` and `grantee_actor_id`; any undeclared field is rejected. Only the attestation's `signer_actor_id` (authenticated as above) may create a grant. The first creation returns `201` with exactly `{id, attestation_id, grantee_actor_id, created_at}` — a stable `aag_` id and a UTC `created_at`. A retried submission for the same `(attestation_id, grantee_actor_id)` pair returns `200` with the original record and writes no new row or audit event; a different grantee forms an independent, immutable record. The first grant write and its `attestation.access_granted` audit event commit in a single transaction. Missing credentials, an unparseable or out-of-window timestamp, malformed signature encoding, a signature no current key of the actor verifies, malformed fields or JSON, a missing attestation, a missing grantee actor, and a caller who is not the attestation's signer are all `422 validation_error`; no failure writes a resource or an audit event.
- `GET /v1/protected/attestations/{attestation_id}` — read-only. Only the attestation's `signer_actor_id` or an actor holding an access grant for that exact attestation may call it; success returns the existing attestation's public view (the same fields as `GET /v1/attestations/{id}`). A missing target, an unauthenticated caller, and an unauthorized caller all return the **same opaque `404 not_found`**, so existence is never revealed to a caller without access. An unparseable/out-of-window timestamp or a signature that is not canonical Base64 of exactly 64 bytes is `422 validation_error`. The read writes no resource and no audit event.
- `GET /v1/attestations/{attestation_id}/access-grants` — read-only, signed with the same `X-PA`/`X-PT`/`X-PS` contract over the empty GET body (the signed path carries no query string). Only the attestation's `signer_actor_id` may call it — a grantee who can read the protected proof cannot list its grants. A missing or unauthenticatable credential, a missing target, and a non-signer all return the **same opaque `404 not_found`**; an unparseable/out-of-window timestamp or a malformed signature is `422 validation_error`. Success is strictly `{"items", "count", "next_cursor"}`; each item carries exactly `{id, attestation_id, grantee_actor_id, created_at}` in stable creation order (`created_at` with the monotonic sequence tiebreaker) and never echoes any revocation, private key, raw signature, authentication header, payload, or byte. Only `limit` and `cursor` are accepted: `limit` is a pure decimal integer in `1..100` (default `50`); any undeclared, repeated, blank/whitespace, or otherwise illegal parameter — and any malformed, unsigned, foreign-family, or non-binding cursor — is `422 validation_error`, checked before the target lookup. The opaque cursor is HMAC-signed and bound to the attestation, the authenticated caller, and the effective limit, so it resumes only the query that minted it; continuation pages repeat and omit nothing, the last page carries `next_cursor: null`, and a position past the tail returns `"items": []` with the same `count`. An attestation without grants returns an empty collection; the route is strictly read-only and leaves the existing grant and protected-read interfaces unchanged.

### Read-only tracking of grant revocations

Reviewers can read the immutable grant-revocation records through two read-only routes. Neither route requires the `X-PA`/`X-PT`/`X-PS` headers, both accept **no query parameters** — any, blank, or repeated parameter is `422 validation_error` validated *before* the resource lookup — and both are strictly read-only: a successful read, an empty result, a missing resource, and a parameter failure create or modify no grant, revocation, other resource, or audit event.

- `GET /v1/attestation-access-grant-revocations/{revocation_id}` — returns one existing revocation's public view, exactly `{id, grant_id, revoker_actor_id, reason, created_at}` with a UTC timestamp. The revocation id is the only lookup key — a grant id or attestation id is never reverse-resolved. An unknown id is an explicit `404 attestation_access_grant_revocation_not_found` carrying the requested `revocation_id` (an unknown id supplied together with a query parameter is the 422, since parameters are checked first). The view carries no private key, raw signature, authentication header, claim payload, content, or evidence byte.
- `GET /v1/attestation-access-grants/{grant_id}/revocations` — returns only that existing grant's revocation records as strictly `{"items", "count"}`, each item the exact five-field public view above, in the records' stable creation order (`created_at` with the monotonic sequence tiebreaker). The grant id is the sole lookup key — records are never resolved through a revoker, reason, attestation, or revocation id. An unknown grant is `422 validation_error` with `details.reason="grant_not_found"` (the same boundary as the revocation write route), never an empty collection and never a reverse lookup; an existing grant that has not been revoked returns `{"items": [], "count": 0}`. Repeated reads are deterministic and the views are unchanged across an app restart.

## Content lineage relations

Relations record how content identities descend from one another: `content_id` is the newer version or derived content, `parent_content_id` is its direct source, and `relation_type` is `version_of` or `derived_from`. Relations are immutable and append-only: there is no update or delete path.

- `POST /v1/content-relations` — create a relation between two existing contents. The first creation returns `201` with the stable `rel_` id, both content ids, the relation type, and a UTC `created_at`; a repeat submission of the same three fields returns `200` with the existing relation and writes no row or audit event. An unknown content on either side is `404 content_not_found`; blank identifiers, an unknown relation type, a self-loop, or an edge that would close a lineage cycle are `422 validation_error` and write nothing.
- `GET /v1/content-relations/{relation_id}` — full public fields, or `404 content_relation_not_found`.
- `GET /v1/contents/{content_id}/relations` — the in- and out-edges of one content in stable creation order as `{"items", "count"}`; an unknown content id is `404 content_not_found`.
- `GET /v1/contents/{content_id}/lineage?direction=ancestors|descendants&max_depth=...&relation_type=...&min_depth=...&limit=...&cursor=...` — read-only multi-hop traversal. `direction` is required and must be exactly `ancestors` (content to direct source, following edges onward) or `descendants` (the reverse); `max_depth` is an optional integer from 1 to 32 defaulting to 8. Optional filters and paging: `relation_type` is exactly `version_of` or `derived_from` (absent means no edge-type filtering); `min_depth` is an integer from 1 to 32 defaulting to 1 and must not exceed the effective `max_depth`; `limit` is an integer from 1 to 100 defaulting to 50; `cursor` is an opaque server token returned by a previous page. Filtering only removes returned items — it never prunes traversal reachability, changes shortest-depth dedup, or changes depth/discovery ordering: an item matches `relation_type` when the edge through which it was *first* reached (at its shortest depth) has that type. Missing/blank/illegal `direction`, an empty/non-integer/out-of-range/repeated `max_depth`, `min_depth`, or `limit`, an unknown `relation_type`, a `min_depth` greater than `max_depth`, and an empty, malformed, tampered, expired-format, or query-parameter-mismatching `cursor` are all `422 validation_error` — nothing is defaulted or silently normalized, and no resource or audit row is written. The origin is never included; only contents reachable within the depth limit are returned, each deduplicated at its shortest depth, ordered by depth ascending and within a level by the discovering edge's stable creation order, as `{"items", "count", "next_cursor"}` where each item is the full public content view plus an integer `depth`. `count` is the total number of items after filtering, independent of the page returned; `next_cursor` is an opaque token for the next page or `null` on the final (and only, for an empty result) page. Re-sending a cursor with the same effective parameters resumes exactly where the previous page ended, with no duplicates or omissions; cursors are HMAC-signed and bind to the origin, direction, and every effective filter/limit value. No reachable contents yields an empty set. An unknown origin is `404 content_not_found`. The query reads only contents and relations (no resource or audit writes), deduplicates visited nodes, and terminates even if anomalous history contains a cycle.

The first relation creation and its `content_relation.created` audit event commit in a single transaction.

## Authentication public-key rotation

A subject can rotate the public key that authenticates its protected-route requests without minting a new attestation. A rotation introduces a new Ed25519 public key that immediately joins the subject's **non-revoked authentication set** — the union of the public keys on the subject's existing non-revoked attestations and the subject's active rotation keys. No new attestation or proof is required, and a public key still carried by an existing non-revoked attestation remains valid. The service never receives a private key or a raw signature. Both routes authenticate with the same `X-PA`/`X-PT`/`X-PS` header contract as the other protected routes, and the authenticated caller is always the rotation's subject.

- `POST /v1/authentication-key-rotations` — JSON body contains exactly a non-empty `actor_id` and a standard-Base64 `new_public_key` that decodes to exactly **32 bytes**; any undeclared field is rejected. The caller must authenticate as that same `actor_id`, which must already exist. The first creation returns `201` with exactly `{id, actor_id, new_public_key, active, created_at, retired_at}` — a stable `akr_` id, the subject, the Base64 public key, `active: true`, a timezone-aware UTC `created_at`, and `retired_at: null`. The first write and its `authentication_key.rotated` audit event commit in a single transaction. A retried submission for the same subject and public key returns `200` with the original record and writes no row or audit event — this stays idempotent even after the record has been retired, in which case the original (now retired) record is returned unchanged. A different public key for the same subject forms an independent rotation.
- `POST /v1/authentication-key-rotations/{rotation_id}/retire` — the request body is **empty** (the signed `body_sha256` is therefore the digest of zero bytes). Only the owning subject may retire a record, and only while it is active. Success returns the record with `active: false` and a timezone-aware UTC `retired_at` (the `akr_` id, subject, and public key are unchanged), and the state change and the `authentication_key.retired` audit event commit in a single transaction. The retired key stops authenticating immediately; the record and its `authentication_key.rotated` history are preserved.
- `GET /v1/actors/{actor_id}/authentication-key-rotations` — read-only reviewer retrieval of one existing subject's key-rotation history; no authentication headers are required. It accepts exactly `limit` and `cursor` (any other parameter, and any repeated parameter, is `422 validation_error` before the subject lookup). Success returns strictly `{"items", "count", "next_cursor"}`; each item is exactly the existing public rotation view `{id, actor_id, new_public_key, active, created_at, retired_at}` — no private key, raw signature, authentication header, or internal ordering surrogate is ever present — and records follow stable creation order (`created_at` with the monotonic sequence tiebreaker), active and retired records together. `limit` is a pure decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token in its own family, bound to the path subject and the effective limit, so pages resume without duplication or omission, `count` is always the subject's rotation total on every page (including a page at or past the tail, which returns empty `items`, the original `count`, and `next_cursor: null`), and the final page carries `next_cursor: null`. Blank, non-integer, out-of-range, signed, decimal, or padded `limit` values; blank, malformed, tampered, wrongly-signed, expired-format, wrong-claim-set, cross-endpoint, or subject/limit-mismatching `cursor` values are all `422 validation_error` — nothing is silently normalized. An existing subject without rotations is an empty collection (`count` 0); an unknown subject is `404 unknown_actor`, decided only after query validation. The read writes no resource and no audit event.

An active rotation key authenticates `POST /v1/attestation-access-grants`, `GET /v1/protected/attestations/{attestation_id}`, `GET /v1/attestations/{attestation_id}/access-grants`, and the two rotation routes exactly as an attestation key would; retiring it removes it from the set at once. The request body and the credentials are validated before any state change. An unknown subject, an unknown rotation id, a caller who is not the record's subject, and a repeat retirement of an already-retired record are all `422 validation_error` (existence is never revealed to a non-owner) and write neither a resource nor an audit event; credential failures use the same `validation_error` code as on the grant route.

## Subject trust policies and authorization decisions

A subject can register one immutable trust policy — the number of distinct qualified signers it requires before a claim or evidence bundle is trusted — and then ask the service for authorization decisions computed under that policy. A policy is append-only and immutable: there is deliberately no update, delete, deactivate, or replace path (any such attempt is `405 method_not_allowed`). Both routes authenticate with the same `X-PA`/`X-PT`/`X-PS` header contract as the other protected routes, and both answer with compact UTF-8 JSON terminated by exactly one newline, with all numbers rendered as integers (never negative zero or a non-finite value).

- `POST /v1/trust-policies` — JSON body contains exactly a non-empty `actor_id` and a `threshold`; any undeclared field is rejected. `threshold` is a pure decimal integer from 1 to 100: booleans, strings, and fractional or exponent-notation numbers are `422 validation_error`, never coerced. The caller must authenticate as that same `actor_id`, which must already exist: an unknown subject and a caller/subject mismatch are both `422 validation_error` and write nothing. The first registration returns `201` with exactly `{id, actor_id, threshold, enabled, created_at}` — a stable `atp_` id, the subject, the threshold, `enabled: true`, and a timezone-aware UTC `created_at` — and the policy row and its `actor_trust_policy.created` audit event commit in a single transaction. Each subject has at most one policy: a retried registration of the same subject and threshold returns `200` with the original policy and writes no new row, audit event, or identifier, while the same subject with a different threshold is `409 actor_trust_policy_conflict` and likewise writes nothing. Missing credentials, an unparseable or out-of-window timestamp, malformed signature encoding, a signature no current key of the actor verifies, malformed fields, and malformed JSON are all `422 validation_error`; no failure writes a resource or an audit event.
- `GET /v1/trust-policies?actor_id=...&limit=...&cursor=...` — read-only retrieval of the existing immutable trust policies; no authentication headers are required. The request body must be empty: carrying any bytes (even whitespace or malformed JSON) is `422 validation_error`, rejected before any parameter or policy is read. The success body is compact UTF-8 JSON terminated by exactly one newline, with members in exactly the order `items`, `count`, `next_cursor`; each item is the existing policy public view (`id`, `actor_id`, `threshold`, `enabled`, UTC `created_at`) in the policies' stable creation order (`created_at` with the monotonic `seq` tiebreaker). Optional `actor_id` is a non-empty, case/whitespace-sensitive exact match on the policy subject (absent means unfiltered) and is never resolved for existence — an unknown subject is an empty collection, not a 404. `count` is the filtered total covering every page, independent of the page returned. `limit` is a pure decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token (its own `tp1` family) bound to the effective `actor_id` (`null` when unfiltered) and the effective limit, so pages resume without duplication or omission and the final page carries `next_cursor: null` (a cursor at or past the tail returns an empty page with the original `count`). Blank/illegal/repeated/undeclared parameters and an empty, whitespace-only, malformed, tampered, cross-endpoint/foreign-family, or filter/limit-mismatching `cursor` are all `422 validation_error` — nothing is silently defaulted or normalized. No match returns `{"items": [], "count": 0, "next_cursor": null}`. The retrieval is strictly read-only: success, empty results, repeated reads, and failures create no policy, resource, or audit event, and the view never carries a private key, raw signature, claim payload, content, or evidence bytes.
- `GET /v1/trust-decisions?target_type=claim|evidence_bundle&target_id=...` — read-only authorization decision under the **calling subject's current policy** (no other subject's policy ever participates). The request carries no body: any body bytes at all (even whitespace or malformed JSON) are `422 validation_error`, checked before the parameters. `target_type` is required and must be exactly `claim` or `evidence_bundle`; `target_id` is required and non-blank; any undeclared, repeated, blank, or illegal parameter is `422 validation_error`, validated before authentication. Missing or unauthenticatable credentials return the same opaque `404 not_found` as the other protected read routes (existence is never revealed); an unparseable/out-of-window timestamp or a malformed signature encoding is `422 validation_error`. When the caller has **no policy**, the target is never looked up — its existence is neither checked nor revealed — and the response is `200` with `{"target_type", "target_id", "policy_id": null, "threshold": null, "qualified_signer_count": 0, "decision": "untrusted", "reason": "policy_missing"}`. With a policy, the target must exist: an unknown target is `404 claim_not_found` or `404 evidence_bundle_not_found` according to the declared `target_type` (claim and evidence-bundle ids never cross-match), never a partial decision. Otherwise the response is `200` with the echoed `target_type`/`target_id`, the deciding `policy_id` and `threshold`, the `qualified_signer_count` (verified, non-revoked attestations of the exact target, deduplicated by signing actor — the same counting as the trust-evaluation route), and the `decision`/`reason` pair: `trusted`/`threshold_met` when the count reaches the policy threshold, `untrusted`/`below_threshold` otherwise. The decision is computed live on every request and is strictly read-only: decisions, no-policy responses, missing targets, and failed requests write no resource and no audit event.

## Audit-event search

Compliance auditors can search the append-only audit trail directly. The endpoint is strictly read-only: it never creates, updates, or deletes any resource or audit row, on success or on failure.

- `GET /v1/audit-events?event_type=...&resource_id=...&from=...&to=...&limit=...&cursor=...` — read-only search over the existing audit events. Returns `{"items", "count", "next_cursor"}` where each item carries exactly `event_type`, `resource_id`, and a timezone-aware UTC `created_at`, ordered by the events' stable creation order. Optional `event_type` and `resource_id` are non-empty, case/whitespace-sensitive exact matches that combine as logical AND; `from` and `to` are strict RFC 3339 UTC instants (e.g. `2026-01-02T12:30:00Z` or `...+00:00`) applied as inclusive `created_at` bounds, and `from` must not be later than `to`. `limit` is an integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token that binds to every effective filter and the limit, so pages resume without duplication or omission, `count` is always the filtered total, and the final page carries `next_cursor: null`. Blank/illegal/repeated/undeclared parameters, a `from` later than `to`, and a blank, malformed, tampered, foreign-family, or filter-mismatching `cursor` are all `422 validation_error` — nothing is silently defaulted or normalized. No matching events yields an empty collection. The query writes no resource or audit rows, and neither does any rejected request.
- `GET /v1/audit-events/checkpoint/package` — read-only one-call export, for an external compliance system, of a filtered audit-event sequence together with its integrity checkpoint. It accepts exactly the four checkpoint filters `event_type`, `resource_id`, `from`, and `to` with the exact-match, strict RFC 3339 UTC, repeated-parameter, and undeclared-parameter semantics of the checkpoint route; `limit` and `cursor` are not accepted, and blank/illegal/repeated/undeclared parameters and a `from` later than `to` are all `422 validation_error`, validated before any event is read. The success body is strictly `{"checkpoint", "events"}`: `checkpoint` is exactly the four-field body of the existing `GET /v1/audit-events/checkpoint` route for the same effective filter (`checkpoint_version="provenance-audit-checkpoint-v1"`, `digest_algorithm="sha256"`, `event_count`, `events_digest_hex`), and `events` lists, in stable creation order, the existing audit-event public views matched by that same filter — each item exactly `{"event_type", "resource_id", "created_at"}` with a timezone-aware UTC timestamp. The checkpoint digest is computed over exactly the `events` array returned in the same response under the existing checkpoint canonical rules (array order kept, object keys sorted by Unicode code point, compact separators, unescaped non-ASCII, UTF-8, SHA-256), and both halves derive from a single read-only state read, so they are always mutually consistent; the returned pair verifies offline via the stateless checkpoint-verification route. An empty match set returns `"events": []` with `event_count: 0` and the digest of the empty array. The route is strictly read-only: success, empty results, and failures create, modify, or delete no resource and add no audit event; repeated reads and reads across an app restart return the same package, and the existing audit-event search, checkpoint, verification, checkpoint-import receipts, identifiers, UTC fields, and error JSON are unchanged.
- `POST /v1/audit-events/checkpoint-imports` — controlled registration, for an external compliance system, of an audit checkpoint that was already received and verified offline. The request body is exactly `{"checkpoint", "events"}`, with the field structure, fixed version/algorithm, event count, strict RFC 3339 UTC timestamps, and canonical digest rules of the stateless checkpoint-verification route: `checkpoint` is exactly `{"checkpoint_version", "digest_algorithm", "event_count", "events_digest_hex"}` with `checkpoint_version="provenance-audit-checkpoint-v1"`, `digest_algorithm="sha256"`, a non-negative integer `event_count`, and a 64-lowercase-hex `events_digest_hex`; `events` is an array of exactly `event_count` items, each exactly `{"event_type", "resource_id", "created_at"}` with non-empty strings and a strict RFC 3339 UTC timestamp. The digest is recomputed over the events exactly as received (array order preserved, object keys sorted by Unicode code point, compact separators, unescaped non-ASCII, UTF-8, SHA-256). Verification is decided by the request body alone: the events described by the checkpoint are never created, modified, or queried against local state, so whether they exist locally cannot change the receipt, and no such event is materialized. Missing or extra top-level or nested fields, wrong member types, the wrong version/algorithm, a malformed digest or timestamp, an event array whose length differs from `event_count`, malformed JSON, and a digest mismatch are all `422 validation_error` and write nothing — a mismatch carries `details.reason="events_digest_mismatch"` and the `computed_digest_hex`. On success the receiving identity is exactly `(checkpoint_version, event_count, events_digest_hex)`; the first submission returns `201` with a stable deterministic `aci_` receipt id, the three identity fields, and a UTC `received_at`, and writes the receipt row together with the `audit.checkpoint_imported` audit event in a single transaction. A retry for the same identity returns `200` with the original receipt (including its original `received_at`) and writes no second row or audit event — even when the retried events themselves no longer match, in which case the retry is `422` and the original record is untouched. The full event array and all raw event data are never copied or persisted: the receipt holds only the identity fields.
- `GET /v1/audit-events/checkpoint-imports/{import_id}` — read the public receipt for one registered checkpoint import: exactly `{"id", "checkpoint_version", "events_digest_hex", "event_count", "received_at"}`, with `received_at` a UTC timestamp. The event array and every raw event datum are never returned. An unknown id is an explicit `404 audit_checkpoint_import_not_found` carrying the requested `import_id`; the read is strictly read-only and writes no resource or audit event.
- `GET /v1/audit-events/checkpoint-imports/{import_id}/reconciliation` — read-only reconciliation, for an external compliance reviewer, of one registered checkpoint-import receipt against the current local audit sequence. The route accepts no query parameters — any parameter or repeated parameter is `422 validation_error`, validated before the receipt lookup — and an unknown id is the existing `404 audit_checkpoint_import_not_found` carrying the requested `import_id`. The success body is strictly `{"import_id", "local_checkpoint", "matches"}`: `import_id` is the receipt id; `local_checkpoint` is the four-field checkpoint (`checkpoint_version="provenance-audit-checkpoint-v1"`, `digest_algorithm="sha256"`, `event_count`, `events_digest_hex`) computed over the complete, unfiltered local audit-event sequence under exactly the existing `GET /v1/audit-events/checkpoint` rules — same fixed version and algorithm, stable creation order, UTC representation, and canonical SHA-256 digest semantics (an empty local sequence yields `event_count: 0` and the digest of the empty array). `matches` is `true` only when the receipt's `checkpoint_version`, `event_count`, and `events_digest_hex` all equal the corresponding local checkpoint fields; any difference (including a local sequence that has since grown or changed) is `false`, with the current checkpoint still reported. The imported event array is never read (it is not persisted) or echoed, and the verdict is never inferred from any unpersisted material. Success, an empty local trail, parameter failures, and a missing receipt are all strictly read-only: no resource, receipt, or audit event is created or modified, and the existing checkpoint, import receipt, audit-event search, identifiers, UTC fields, and error JSON are unchanged.
- `GET /v1/audit-events/checkpoint-import-reconciliations?limit=...&cursor=...` — read-only, paginated reconciliation of every existing checkpoint-import receipt against the current local audit sequence. Only `limit` and `cursor` are accepted: any undeclared, repeated, blank, or illegal parameter is `422 validation_error`. The success body is strictly `{"items", "count", "next_cursor"}`; receipts are returned in the same stable creation order (`created_at` with the monotonic `seq` tiebreaker) and `count` is the total number of receipts, independent of the page. Each item is the existing single-receipt public view (`id`, `checkpoint_version`, `events_digest_hex`, `event_count`, UTC `received_at`) plus `local_checkpoint` and `matches`; `local_checkpoint` is the four-field checkpoint computed over the complete, unfiltered local audit sequence under exactly the existing `GET /v1/audit-events/checkpoint` rules, and `matches` is `true` only when the receipt's version, event count, and digest all equal that checkpoint — agreeing item-for-item with the single-receipt reconciliation route. `limit` is a pure decimal integer from 1 to 100 defaulting to 50; `cursor` is an opaque HMAC-signed server token (its own `cr1` family) binding to the effective limit, so pages resume without duplication or omission and the final page carries `next_cursor: null` (a cursor at or past the end returns empty `items`, the total `count`, and `null`; an empty, malformed, tampered, foreign-family, or limit-mismatching cursor is `422 validation_error`). No receipts is an empty collection (`{"items": [], "count": 0, "next_cursor": null}`). The imported event arrays are never read or echoed; the route is strictly read-only and writes no resource, receipt, or audit event, and it is compatible with the existing single-receipt reconciliation, checkpoint, receipt search, and error JSON.

Errors are distinct JSON bodies under `{"error": {"code", ...}}`: `actor_already_exists` (409), `unknown_actor` (404), `content_not_found` (404), `claim_not_found` (404), `evidence_bundle_not_found` (404), `attestation_not_found` (404), `attestation_revocation_not_found` (404), `attestation_access_grant_revocation_not_found` (404), `content_relation_not_found` (404), `content_export_job_not_found` (404), `content_export_request_conflict` (409), `actor_trust_policy_conflict` (409), `attestation_verification_failed` (422), and `validation_error` (422); the protected attestation read answers a missing target, an unauthenticated caller, and an unauthorized caller with one opaque `not_found` (404); a content export job that is not pending when run returns `conflict` (409), and a failed run records `content_export_failed` in the job's `error` field (the run itself returns `200`). Every successful actor, content, claim, evidence bundle, attestation, attestation revocation, attestation access grant, content relation, authentication key rotation, and actor trust policy creation appends one audit row (`event_type`, `resource_id`, UTC `created_at`) in the same transaction as the resource write; a revocation records the `attestation.revoked` event, an access grant records the `attestation.access_granted` event, a rotation records the `authentication_key.rotated` event, retiring a rotation records the `authentication_key.retired` event, a content export job creation records the `content_export_job.created` event, running an export job records the `content_export_job.run` event, and a trust policy registration records the `actor_trust_policy.created` event. All returned timestamps are timezone-aware UTC.
